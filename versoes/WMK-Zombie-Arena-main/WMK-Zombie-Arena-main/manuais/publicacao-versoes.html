Manual de versões, código-fonte e GitHub Pages

WMK Zombie Arena • Walney Moreira Klein — walneyk@hotmail.com

Aprenda a desenvolver, testar, publicar e recuperar versões sem perder os fontes.

1. As três peças do projeto

LocalFunção
mainVersão estável e código-fonte integral. GitHub Actions publica esta branch no Pages.
developPróximas alterações ainda não liberadas ao público.
vX.Y.Z (tag)Marca uma versão imutável. GitHub Releases cria o ZIP com os fontes dessa revisão.

O Pages executa HTML/CSS/JS do mesmo repositório: não é um segundo jogo. O servidor GitHub Pages não hospeda backends de multiplayer.

2. Começando a trabalhar sem afetar jogadores

git clone https://github.com/WalneyNF/WMK-Zombie-Arena.git
cd WMK-Zombie-Arena
git fetch origin
git switch develop
git pull origin develop
# faça suas alterações, teste e só então publique
git add .
git commit -m "feat: melhorias no jogo"
git push origin develop

Se a branch develop não existir localmente, use git switch -c develop --track origin/develop.

3. Testar localmente

py -m http.server 5500

Acesse http://localhost:5500/. Teste: tela inicial, armas, tiros, recarga, editor, exportação/importação de JSON, mapas, sons, câmera, consoles de erro F12 e consumo de memória. Não execute pelo protocolo file://. Confirme os caminhos relativos para /WMK-Zombie-Arena/.

Teste também em janela anônima, sem depender de dados previamente salvos no localStorage.

4. Publicar a versão oficial

Depois de revisar o código, abra um Pull Request de develop para main. Revise os arquivos alterados e execute o merge. O workflow .github/workflows/pages.yml executa verificações e implanta o site. Confira em GitHub Actions. O site oficial é WMK Zombie Arena.

Não envie um protótipo incompleto diretamente à main: isso altera a versão pública. Um commit ou tag não garante que o deploy tenha funcionado; verifique a execução no Actions.

5. Criar ZIP de uma versão

Após a publicação estável, marque o commit da main com uma tag, por exemplo:

git switch main
git pull origin main
git tag -a v1.8.7 -m "WMK Zombie Arena v1.8.7"
git push origin v1.8.7

O workflow .github/workflows/release.yml é acionado pelas tags no formato v* e cria um Release com um ZIP contendo o código-fonte, os mapas, os recursos e a documentação daquele commit. Verifique a aba Releases. Use outro número de versão quando o conteúdo mudar; não reescreva tags públicas.

Importante: versões geradas no ChatGPT ou ZIPs locais não chegam ao GitHub automaticamente. É preciso enviar esses arquivos ao repositório antes de criar a tag.

6. Recuperação após um erro

Consulte o histórico de commits e Releases. Para reverter uma atualização sem apagar o histórico:

git switch main
git pull
git revert <SHA_DO_COMMIT>
git push origin main

Para várias alterações, prefira um Pull Request de correção ou restauração de uma tag anterior. Evite git push --force na main.

7. Política de versões

MAJOR.MINOR.PATCH: MAJOR altera compatibilidade de formatos/API; MINOR adiciona recursos compatíveis; PATCH corrige erros. Exemplo: 1.8.7. Cada lançamento deve ter registro de mudanças, arquivos fontes completos e testes mínimos. Mantenha version.json e a interface sincronizados quando atualizar a versão.

8. Colaboração

Contribuidores criam uma branch, documentam as mudanças e abrem Pull Requests. Para mapas, armas, zumbis e skins, envie JSON, arquivos 3D ou imagens com licença compatível e instruções de teste. Não publique arquivos de jogos comerciais sem autorização.

9. Solução de problemas

ProblemaO que verificar
Pages mostra jogo antigoCommit da main, job de deploy, cache (Ctrl+F5), caminho do site.
Faltam armas ou mapasArquivos JSON/GLB no commit, caminhos relativos e mensagens do F12.
O ZIP não foi criadoTag foi enviada? Workflow release foi executado? Permissão contents:write?
JSON do editor desapareceuImporte o arquivo exportado; localStorage não substitui backup.
